# 文昌智脑 V1.5：联网搜索反爬故障与标准 Search API Provider 改造报告

> 记录时间：2026-08-11  
> 事件类型：生产型 Agent 工具链故障 / 外部 Provider 稳定性  
> 状态：代码修复、测试与部署完成；正式联网成功仍需配置 Tavily 或 Brave Search API Key

## 1. 案例摘要

用户向文昌智脑提出：

> 帮我联网搜索文昌最新的 10 条新闻。

Agent 正确识别了问题的时效性，DeepSeek 也正确决定调用 `webSearch` Native Tool，但工具没有返回新闻。最终回答只能如实提示：

```text
provider=sogou
status=UNAVAILABLE
HTTP 302 anti-bot challenge
```

这不是“模型不会联网”，也不是 MCP 故障，而是搜索工具依赖搜狗 HTML 页面，入口被反爬系统重定向到验证页。旧实现把一个面向人类浏览器的网页入口当成了生产搜索接口，缺少标准 API、故障转移、缓存、熔断和清晰的运行状态。

本轮将搜索层改造成可替换的生产架构：

- Tavily 官方 JSON Search API；
- Brave Search 官方 JSON API；
- `auto` 有序故障转移；
- 429、5xx、超时的限次重试与短退避；
- 单 Provider 熔断与冷却；
- 查询结果 TTL 缓存；
- canonical URL 去重；
- 新闻查询的近期时间窗口；
- 发布时间与 Provider 来源元数据；
- 搜狗 HTML 仅作为显式开启的可选降级；
- 没有 API Key 时准确报告 `SEARCH_API_NOT_CONFIGURED`。

## 2. 真实现象与证据

### 2.1 用户可见现象

Agent 没有编造 10 条新闻，而是说明联网搜索未完成，并把知识库中的事实性资料明确标为“非最新新闻”。这部分降级行为是正确的。

### 2.2 Trace 证据

真实失败链路：

```text
traceId = be3f9fbd-005d-4946-b752-a070d4fa528f
query = 帮我联网搜索文昌最新的10条新闻
toolName = webSearch
toolSource = NATIVE
stage = TOOL_EXECUTION
status = FAILED
errorType = ANTI_BOT
latencyMs = 167
provider = sogou
detail = HTTP 302 redirect to anti-bot challenge
```

受控请求确认 `302 Location` 指向搜狗的 `antispider` 验证入口。网络连接已经建立，服务端也已经返回 HTTP 响应，因此它不是普通断网或 DNS 故障。

### 2.3 A-I 根因分类

| 分类 | 结论 | 证据 |
|---|---|---|
| A. DeepSeek 未发 Tool Call | 否 | Trace 中存在 `webSearch` 调用 |
| B. Capability Router 未路由 | 否 | 时效问题已进入联网检索链路 |
| C. Native Tool 未注册 | 否 | `webSearch` 已注册并执行 |
| D. Web Search Provider 失败 | **是，主根因** | 搜狗返回 302 anti-bot challenge |
| E. Official Search Provider 失败 | **是，连带影响** | 权威检索复用同一底层 SearchProvider |
| F. MCP Server 未连接 | 否 | MCP 独立健康，且此工具为 Native Tool |
| G. MCP Tool 未发现 | 否 | 与本次 Native Tool 失败无关 |
| H. Tool 执行框架异常 | 否 | ToolCallback 正常进入并返回结构化失败 |
| I. 一般网络异常 | 否 | 已收到明确 HTTP 302 响应 |

## 3. 为什么这是一个典型的 Agent 工程 Bug

传统聊天系统只需判断“有没有回答”；Agent 系统必须继续追问：

1. 模型是否选择了正确工具？
2. 工具是否已注册？
3. 工具来自 Native 还是 MCP？
4. 外部 Provider 是否健康？
5. 失败属于鉴权、限流、超时、上游错误还是反爬？
6. 失败后是否继续使用已有证据，而不是编造实时结果？
7. 用户界面是否能把技术错误和正文回答分开？

本案中 DeepSeek、Tool Calling、Spring AI ToolCallback 和 Trace 都正常，真正不稳定的是最后一公里的数据 Provider。若只检查 HTTP 200 的聊天响应，就会错误地认为整个 Agent 已通过验收。

## 4. DeepSeek 能力边界

DeepSeek 的标准 Chat Completions API 支持 Tool Calls：模型选择函数和参数，应用负责真正执行函数，再把工具结果交给模型生成最终回答。开发者仍需提供实际搜索能力。

DeepSeek App 的“联网搜索”产品功能，或其他 DeepSeek Agent 集成中的 `webSearchTool`，不能等价为标准 Chat Completions API 自动附带网页检索。文昌智脑必须在自己的 Tool 层连接可靠的 Search Provider。

官方参考：

- [DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls)
- [DeepSeek Chat Completion API](https://api-docs.deepseek.com/api/create-chat-completion)
- [DeepSeek App Web Search announcement](https://api-docs.deepseek.com/news/news250115/)
- [DeepSeek Deep Code agent integration](https://api-docs.deepseek.com/quick_start/agent_integrations/deepcode)

## 5. 方案取舍

### 5.1 没有采用的方案

- 轮换代理 IP；
- 自动绕过验证码；
- 伪造大量浏览器指纹；
- 持续变更 User-Agent 规避封禁；
- 对反爬页面做对抗性解析。

原因：这些方案不稳定、维护成本高，可能违反站点使用条款，也会把业务可用性建立在不可控的对抗上。

### 5.2 采用的方案

使用面向程序调用的正式 JSON Search API，并把稳定性能力放在 Provider 编排层：

```text
DeepSeek
  ↓ tool_call
webSearch (Native Tool)
  ↓
ResilientSearchProvider
  ├─ cache hit → return
  ├─ Tavily → success
  ├─ Tavily failure → retry/backoff/circuit
  ├─ Brave → failover success
  └─ all unavailable → structured failure
```

候选 Provider 的官方接口：

- [Tavily Search API](https://docs.tavily.com/documentation/api-reference/endpoint/search)
- [Tavily Quickstart](https://docs.tavily.com/documentation/quickstart)
- [Brave Search API](https://api-dashboard.search.brave.com/api-reference/web/search/get)
- [Brave Search API getting started](https://api-dashboard.search.brave.com/app/documentation/web-search/get-started)

## 6. 实现内容

### 6.1 Provider 接口

统一接口继续保持：

```java
String id();
List<WebSearchResult> search(String query, int limit);
SearchProviderHealth healthCheck();
SearchProviderHealth currentHealth();
```

业务 Tool 不依赖 Tavily、Brave 或搜狗的具体协议。

### 6.2 Tavily Provider

- `POST /search`；
- Bearer Token；
- `topic=news` 用于新闻型查询；
- 新闻查询限定近 30 天；
- 解析 `title / url / content / published_date`。

### 6.3 Brave Provider

- `GET /res/v1/web/search`；
- `X-Subscription-Token`；
- 新闻型查询增加 `freshness=pm`；
- 解析 Web 与 News 结果；
- 保留 `page_age / age`。

### 6.4 可靠性编排

`ResilientSearchProvider` 提供：

- 配置顺序故障转移；
- 5 分钟默认缓存；
- 同查询和 limit 的缓存键；
- canonical URL 去重；
- 连续 3 次失败后默认熔断 60 秒；
- 熔断期跳过故障 Provider；
- 成功后自动复位；
- 聚合健康状态与实际命中的 Provider 名称。

### 6.5 HTTP 错误分类

| 情况 | errorType | 策略 |
|---|---|---|
| 401 / 403 | `AUTHENTICATION_FAILED` | 不重试，尝试下一 Provider |
| 429 | `RATE_LIMITED` | 一次短退避重试，再故障转移 |
| 5xx | `UPSTREAM_ERROR` | 一次短退避重试，再故障转移 |
| Socket timeout | `TIMEOUT` | 一次短退避重试，再故障转移 |
| I/O 错误 | `NETWORK_ERROR` | 限次重试，再故障转移 |
| 无 Key | `SEARCH_API_NOT_CONFIGURED` | 明确提示配置 |
| HTML 反爬 | `ANTI_BOT` | 不绕过；仅在显式 HTML 降级时可能出现 |

### 6.6 结果模型

搜索结果从三字段升级为：

```text
title
url
snippet
publishedAt
sourceProvider
```

这使“最新新闻”能够保留时间证据，也能在 Trace 和答案中识别结果来自哪个 Provider。

## 7. 配置方式

推荐复制：

```powershell
Copy-Item config/local-secrets.properties.example config/local-secrets.properties
```

至少填写一个 Key：

```properties
wenchang.web-search.provider=auto
wenchang.web-search.tavily-api-key=
wenchang.web-search.brave-api-key=
wenchang.web-search.fallback-order=tavily,brave
wenchang.web-search.allow-html-fallback=false
```

或使用环境变量：

```powershell
$env:WENCHANG_TAVILY_API_KEY="填写真实 Key"
$env:WENCHANG_BRAVE_API_KEY="填写真实 Key"
$env:WENCHANG_SEARCH_PROVIDER="auto"
```

兼容变量 `WENCHANG_SEARCH_API_KEY` 会作为 Tavily Key 使用。

密钥不写入日志、Trace、错误响应或本报告。

## 8. 健康与诊断修复

旧 `/api/health` 只根据 `enabled=true` 把搜索显示为 READY，无法反映真实 Provider 状态。

现在健康接口返回真实字段：

```json
{
  "webSearchStatus": "UNAVAILABLE",
  "webSearchProvider": "auto",
  "webSearchErrorType": "SEARCH_API_NOT_CONFIGURED"
}
```

`GET /api/admin/diagnostics/agent` 继续返回更完整的 Provider、Health、Latency、Last Success、Last Error 与 Error Type。

## 10. 修复前后对比

| 项目 | 修复前 | 修复后 |
|---|---|---|
| 默认入口 | 搜狗 HTML | `auto` 标准 JSON API |
| Provider | 单一 | Tavily + Brave，可扩展 |
| 故障转移 | 无 | 有序自动切换 |
| 重试 | 无统一策略 | 仅对 429、5xx、超时限次重试 |
| 缓存 | 无 | TTL 查询缓存 |
| 熔断 | 无 | 连续故障熔断与冷却 |
| 时间信息 | 丢失 | 保留发布时间/页面年龄 |
| Provider 来源 | 丢失 | 保留 `sourceProvider` |
| 反爬处理 | 搜索直接失败 | HTML 默认禁用，不做对抗绕过 |
| 无 API Key | 可能误入 HTML 抓取 | 明确 `SEARCH_API_NOT_CONFIGURED` |
| `/api/health` | enabled 即 READY | 返回真实状态和错误类型 |

## 11. 可用于面试的讲述框架

### Situation

构建一个 Spring AI + DeepSeek 的任务型 Agent。用户询问最新新闻时，模型正确调用工具，但产品仍无法返回实时结果。

### Task

判断问题位于模型、路由、Tool Registry、MCP、网络还是外部搜索 Provider，并把一次性修复升级为可维护的生产架构。

### Action

1. 用 Trace 逐层排除 DeepSeek、Capability Router、Native Tool 与 MCP；
2. 用 HTTP 状态和 Location 定位搜狗 302 反爬；
3. 将网页抓取替换为 Tavily/Brave 标准 API 适配器；
4. 增加故障转移、缓存、限次重试、熔断、去重和健康检查；
5. 保留发布时间与 Provider 元数据；
6. 默认关闭 HTML 抓取，明确合规边界；
7. 用契约测试和全量回归验证。

### Result

- Root Cause 从模糊的“联网失败”精确到 `ANTI_BOT`；
- 生产默认不再依赖搜狗 HTML；
- 搜索 Provider 可替换、可诊断、可降级；
- 全量 66 项 Maven 测试通过；
- 当前缺少商业 Search API Key 时，系统准确报告配置缺口而不伪造成功。

## 12. 后续生产动作

要完成“文昌最新 10 条新闻”的真实最终验收，还需：

1. 申请 Tavily 或 Brave Search API Key；
2. 写入 `config/local-secrets.properties` 或环境变量；
3. 重启主服务；
4. 在设置 → 系统状态执行智能体自检；
5. 再次发送“帮我联网搜索文昌最新的 10 条新闻”；
6. 检查 Trace 中 Provider、发布时间、来源 URL、工具状态和耗时；
7. 对新闻按发布日期、相关性和官方来源等级复核。

商业 Search API 的配额与价格可能变化，应以服务商当日官方页面为准。这个外部依赖与 DeepSeek Token 费用是两类不同成本：DeepSeek 负责推理与 Tool Calling，Search API 负责实时网页索引和检索服务。
